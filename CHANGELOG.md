# Changelog

All notable changes to zot, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/).

## [0.20.1] - unreleased

### Performance

- **Listing a session history no longer reads every conversation back.** `session.List` - which stands behind `zot sessions`, `zot --resume last`, and the automatic continuation of an unfinished run that every dispatch performs - loaded each log in full: every message text, every captured tool output, decoded into memory only to throw all of it away but the task line and the outcome. A project run unattended accumulates one log per run, so the cost of starting any order climbed with everything ever run: measured against a directory of 600 logs (~190 MB), a single-order dispatch paid ~1.2 s before its first provider call (0.18 s with a small history), `zot sessions` took 1.24 s, and both scale linearly into minutes as the months accumulate. The listing now scans each log for just what it shows - the meta record's task and provenance, whether a result closed it, and which result - and never hands a message or event payload to the decoder. The same 600-log directory lists in 0.07 s and dispatch costs no more than it does with an empty history; on a synthetic benchmark the scan is ~35x faster than reading whole (`go test ./internal/session -bench OverHistory`). Nothing else changed: resumes, exports and receipts still read logs whole, and listings are byte-identical for logs of every shape - concluded, resumed, compacted, crashed mid-line, or written by anything other than zot's own encoder.

### Fixed


- **Asking zot for help now succeeds.** `zot --help` (and `zot -h`) went through pflag's built-in handling: the usage block was dumped on stderr, a stray `pflag: help requested` line was printed on stdout, and the exit status was 2 — so `zot --help | less` showed one useless line, the text never reached a pipe or a file where it was pointed, and anything scripting around the command saw it fail. The first command anyone runs was broken. Help is now a real flag on every surface that takes one: `zot --help`/`-h`, `zot new --help`, `zot sessions --help` and `zot sessions export --help` each print their usage to stdout and exit 0, before any validation runs (`zot new --provider x --help` answers with help rather than refusing), and without scaffolding anything. Error paths are unchanged: an unknown flag still explains itself on stderr with a non-zero status, so asking for help and being wrong keep their separate audiences.

- **A masked upstream failure no longer reads as the model producing nothing.** A gateway can dress an upstream provider's failure as a normal completion: the chat-completions frame carries `finish_reason: "stop"` with empty content while the real cause sits in `native_finish_reason` (`"network_error"` is the one seen in the wild, from a stealth endpoint dropping every request that carried tool definitions). The transport parsed `finish_reason` and ignored the native one, so the empty turn reached the loop as a clean stop — it nudged the dead provider three times and then ended the run with "the model repeatedly produced nothing", blaming the model for the gateway's fault and burning a scheduled run on a silent misdiagnosis. The chat transport now reads `native_finish_reason`, and an otherwise-empty turn whose native reason names a failure is surfaced through `streamFailure` — the retriable provider error it always was — so the run retries instead of giving up, and an operator reading the log sees the upstream failure rather than a false accusation. The check fires only on a turn that produced no token, reasoning, or tool call, so a real answer that happens to carry an unusual native reason is never discarded.

### Changed

- **The installer is part of the tool, not the website.** `install.sh` - the script `https://zot.im/install.sh` serves - lived only in the website repository, a second copy to keep in step with what the releases actually ship. It now lives in the tool repository as the single source of truth and is published as a release asset on every tag, so `https://github.com/openzot/openzot/releases/latest/download/install.sh` always serves the current installer. The website no longer hosts its own copy: `zot.im/install.sh` proxies to the repo's script, so the one-line install command is unchanged while the script behind it can no longer drift.

## [0.20.0] - 2026-08-24

### Added

- **Skills can change while a run is live.** The engine re-rendered the skills block into the system prompt on every iteration, but the set it rendered was frozen at construction: `Options.Skills` was a `[]Skill` set once and never touched. A skill that appeared after the run started — dropped into a watched directory by the operator, or cloned onto disk by the agent itself mid-hunt — was invisible until the process restarted. `Options.Skills` (and `agent.ExecuteWithToolsOptions.Skills`) is now a `func() []Skill`, asked afresh each time the prompt is built, so a skill that exists by the next turn is described to the model on that turn. Nothing polls and nothing watches — it rides the per-iteration `buildRequest` that was already there.

  The `agent` package carries the machinery to use this: `NewSkillLoader(static, dirs...)` returns a loader whose `Skills` method rescans its directories on every call, merged over a static set (a directory skill wins a name clash, so a downloaded skill can override a shipped default), falling back to the last good set if a directory turns unreadable mid-run rather than blanking the model's capabilities. `StaticSkills(skills)` adapts a fixed slice for a caller that does not need the dynamic behaviour. zot wires the loader over the context directories (`skills/`, `.skills/`) automatically, so `zot` picks up a `SKILL.md` added to a project while it works.

- **An end-of-run digest, and the session id to resume it.** A run ended without ever telling the operator the one thing they most need afterwards: the session to continue. The full-screen viewer runs in the alternate screen, so its live stats — iterations, tokens — vanish when the terminal restores; the streaming renderer ended on a prose line with no numbers; and the session id was never printed at all, only captured internally for the ledger. Every run now closes with a compact block on stderr: `status`, `session`, a ready-to-copy `resume` command, `iterations`, `calls`, `input-tokens`, `output-tokens`, and the ending `message`. The shape is the simplest thing that is both readable and trivial to parse — one row per line, a single-word key, the value as the rest of the line, no borders and no ANSI — so it survives being piped through `grep` or `awk`. Empty fields are omitted, so a run with no session recorded simply has no `session`/`resume` rows.

  The pieces are public in the packages an embedding tool already uses: `tui.RenderDigest(Digest)` formats the block and `tui.DigestStatus(reason, code)` maps an ending to `done`/`failed`/`cancelled`; `agent.Summary` grew `InputTokens`/`OutputTokens` (the billed totals, previously dropped on the floor after the run); `agent.SummaryRecorder` captures the final `Summary` for a caller to read once the run returns; and `agent.MultiRecorder(...)` fans the engine's single recorder to several sinks (a session log and that capture, say).

- **The billed token totals are persisted, so a record carries cost.** The digest showed `input-tokens`/`output-tokens`, but they lived only on the terminal that ran the job: the session log's `Result` and the ledger receipt recorded iterations and calls and dropped the token counts, so an audit or a resumed run could see the *shape* of the work but never what it cost. `session.Result` and `order.Evidence` now carry `InputTokens`/`OutputTokens` too, copied from the run's `Summary` the same way every other field is - never computed at read time, so a receipt stays evidence rather than a claim. Both are `omitempty`, so a log written before this reads back cleanly with the counts simply absent rather than wrong.

### Changed

- **Every skill is now read the same way — with `read`, at a path.** A skill's instructions used to be reached one of two ways depending on where it lived: a skill on disk was read with the `read` tool at its file path, while a skill compiled into the binary was served by a separate `skill` tool that returned its body from memory. Two tools, two verbs, and a `skill` tool whose list of valid names was a snapshot taken at startup — which is exactly the thing that could not represent a skill added mid-run. An embedded skill is now addressed by an `embedded-skill:///<name>` URL — the scheme is self-describing, so the model infers that the skill lives in the binary from the protocol alone rather than from a sentence in the prompt — and the `read` tool resolves that URL against the embedded set instead of the filesystem. Everything after resolution — the required line range, the line-numbered output, the truncation bound — is identical to reading a file, because it *is* the same code path. The model learns one tool and one mental model: a skill is something you `read` at the path its `<access>` line gives, whether that path is `/project/.skills/x/SKILL.md` or `embedded-skill:///x`.

  For callers: `agent.ToolOptions` grew an `EmbeddedSkills map[string]string` field (name → body) that the `read` tool serves against `embedded-skill://` URLs; build it from `SkillsResult.EmbeddedContents()`. A caller that ships embedded skills must pass that registry when it builds the tool set, or the `embedded-skill://` paths those skills advertise will not resolve. `SkillURL`, `SkillNameFromURL`, and `SkillsResult.EmbeddedContents` are the public helpers.

### Removed

- **The `skill` tool is gone**, along with `SkillsResult.Tool()`. It existed only to serve embedded skill bodies that had no filesystem path; now that `read` resolves `embedded-skill://` URLs, there is nothing for it to do. Its removal also deletes the startup name-snapshot that made it unable to describe skills added after a run began. A run with no embedded skills — zot's own default — never registered it anyway, so only embedding applications that shipped a compiled-in skill library (rook) are affected, and the migration is one line: pass `EmbeddedSkills` to `DefaultToolsFor` instead of merging in `Tool()`.

## [0.19.2] - 2026-08-24

### Added

- **Session recording is a public package.** `internal/session` held the durable run log — the meta, messages, events and result of a run, plus the conversations a compaction discarded — but `internal/` is invisible to other modules. A separate Go module like rook (`github.com/pdparchitect/rook`) cannot import `github.com/openzot/openzot/internal/session`, so embedding applications had no way to record or resume runs. The new `github.com/openzot/openzot/session` package re-exports the types an embedding application needs (`Writer`, `Session`, `Meta`, `Entry`) and the functions to drive them (`Start`, `Load`, `List`, `Resolve`, `NewRecorder`), the same pattern the `agent` and `tui` packages already follow. No behaviour changed in zot itself; the engine's session logging is untouched.

## [0.19.1] - 2026-08-23

### Added

- **The update check can be turned off.** A release build asks GitHub for the latest release during every run - the one request zot makes that is not to the configured provider, and until now there was no way to stop it. `update_check.disabled: true` in the config, or `ZOT_UPDATE_CHECK_DISABLED=true`, makes no call at all: not a call whose answer is hidden, no call, for the air-gapped hosts and locked-down CI jobs where the request itself is the problem. Documented in [docs/configuration.md](docs/configuration.md#the-update-check) and [docs/safety.md](docs/safety.md).

### Fixed

- **The header no longer jitters as the numbers grow.** Every live stat in the meta bar was rendered at its natural width, so nine iterations becoming ten, 999 tokens becoming 1.0k, or a rate gaining or losing its decimal shoved every segment after it a column sideways - on every tick, in the one line that is meant to be read at a glance. Each value now sits in a fixed-width cell sized to the widest figure the stat normally shows (a count against its limit is as wide as the limit twice over; tokens, rate and pace have cells of their own), flush against its label with the slack trailing, so the segments after it stay put. A value that outgrows its cell still renders whole; the bar shifts once rather than clipping a digit.

### Changed

- **The update notice says how to upgrade.** It used to name the new version and link the release page; now it also gives the one-line installer, `curl -fsSL https://zot.im/install.sh | bash`, which fetches the latest release for the platform, verifies its checksum and replaces the binary in place.

## [0.19.0] - 2026-08-22

### Added

- **`zot sessions export` turns session logs into trajectories.** A session log is zot's own shape - fine-grained, resumable, and nothing else reads it. The new subcommand renders sessions in the chat convention the rest of the ecosystem speaks (`system`, `user`, `assistant` with `tool_calls`, `tool`), one JSON object per session with the task, model, outcome, timings and event counts beside the conversation: a file of these is a dataset, not a format somebody has to write a parser for. Reasoning, tool calls and the answer that zot records as separate turns fold into one assistant message; each tool result names the call it answers; every message keeps zot's own `type` next to its `role`, so a compaction checkpoint is still told apart from the brief.

  `zot sessions export` prints the last session as one line on stdout; `--out DIR` writes `<id>.jsonl` files and copies the screenshots the model was shown into `images/`, referenced by relative path; `--all` exports every finished chain; `--snapshots` keeps the conversations that compaction or a resume superseded, oldest first, for anyone who wants every turn that happened rather than the final state. A resumed run exports as one trajectory with its `chain` of sessions behind it. `Session` now also exposes `Discarded` (the conversations a reset threw away) and `Started` / `Ended`.

## [0.18.0] - 2026-08-22

### Removed

- **zotui is gone.** The browser command center - `cmd/zotui`, its worker dispatch, compute backends, SQLite store and embedded web app - has been removed, along with `zotui.example.yaml`, `make dev-ui`, `make worker-assets` and `docs/zotui-configuration.md`. It was a worthwhile experiment, but it pulled attention (and a second binary, a database driver and a vendored front end) away from the thing zot actually is: the harness that takes a work order and runs it to completion. Release archives and the container image now ship `zot` alone; the image no longer exposes port 8080 or sets `ZOTUI_*`. Anything zotui did on a schedule is better served by the [GitHub Actions](https://github.com/openzot/actions), which run the same binary in CI.

## [0.17.2] - 2026-08-22

### Fixed

- **A failure delivered inside an open stream is retried.** Both transports turned an error object arriving mid-stream into a bare `Error{Status: 0}` carrying whatever prose the gateway chose, which matched no pattern and carried no status - so the classifier called it permanent and ended the run without a single retry. OpenRouter's wording for it, `JSON error injected into SSE stream`, cost an unattended shift nineteen minutes of finished work; the run before it had gone the same way to `Upstream idle timeout exceeded`, and the one before that to something else again.

  Chasing each new wording is a losing game, so this is classified on structure instead. A request the provider objects to never gets a stream at all - it is refused with a 4xx before a byte of body exists - so an error that arrived *after* the response began is about the generation rather than the asking, and asking again is the right move. Both transports now mark these, and `IsRetriable` honours the mark whatever the message says. A context-length rejection is still detected first, so a thread that genuinely does not fit compacts rather than retrying, and the same prose arriving as a plain 4xx stays permanent.


## [0.17.1] - 2026-08-22

### Added

- **zot names itself to the gateways that rank the apps calling them.** OpenRouter publishes site rankings and Vercel's AI Gateway publishes app leaderboards, both built from two optional headers on each request - and zot sent neither, so every call it had ever made was anonymous and zot appeared on neither list. Both gateways settled on the same pair (`HTTP-Referer` for the project link, `X-Title` for the name), so this is one implementation rather than one per gateway. Applied in `Config.Resolve`, the single point every configuration passes through, so it reaches a run however the client was built.

  What travels is zot's own name and repository URL - the same two values for every zot in the world, carrying nothing about the user, the run or the work. It is sent **only** to those two gateways: a first-party API reads neither header, so sending one there would tell a model provider which tool is calling for no benefit to anyone. Configurable through a top-level `attribution:` block (`name`, `url`, `disabled`) and the matching `ZOT_ATTRIBUTION_*` variables - set `name`/`url` to attribute a tool built on zot, or `disabled: true` to appear nowhere. An explicit header on the provider connection still wins, matched case-insensitively so a hand-written `http-referer` is respected rather than joined by a second one.

## [0.17.0] - 2026-08-22

### Added

- **An agent can look at an image.** A run could produce a screenshot and never see it: `read` split a PNG on newlines and handed the model thousands of replacement characters, so the only way to check a rendering was to decode the pixels by hand and reason about the numbers. zot now carries images end to end. A `view` tool reads an image file, reduces it to a sane size, and the engine attaches it to the conversation; both wire formats grew the parts to carry it (`image_url` on chat-completions, `input_image` on the Responses API). Three details are worth knowing:

  - **The image does not travel in the tool result.** No OpenAI-compatible endpoint accepts image parts on a tool message, so `view` returns text - `attached /tmp/shot.png (image/png, 1100x750)` - and the images are attached to a message of their own, once per turn, after every tool result the turn produced. A user message wedged between two tool results would invalidate the turn.
  - **`view` is only offered to a model that can be shown one.** The catalogue gains `SupportsVision`, and its default for an unrecognised model is *no* - the opposite of tools, because the failure modes are not alike: a model wrongly assumed to take tools fails on its first turn, loudly and cheaply, while one wrongly assumed to see is sent an attachment its endpoint rejects mid-run, or silently drops. So a model zot has not catalogued is never offered the tool and never told images exist, and `read` handed an image says what it is rather than returning mojibake. A model entry can now override what the catalogue believes with `vision:`, `tools:` and `reasoning:` - each a tri-state, where unset defers to the catalogue.
  - **A session log does not swell with base64.** The log is JSON Lines so it can be tailed while a run is going and survive a crash mid-line; a megabyte of base64 on one line defeats both, and a caller that caches its session directory between runs would be caching screenshots. So the bytes go to `<session-id>.blobs/<digest>.png` beside the log, content-addressed - the same screenshot attached twice is stored once - and the record keeps the shape, the digest and the estimated cost. A resumed run rehydrates by digest; a blob that has been deleted since is not an error, because the message text was written to describe the image on its own.

### Changed

- **Recovery bounds count consecutive attempts, not a run's lifetime.** `max_continuations` was spent by every recovery a run ever made - a truncated answer continued, a context-limit compaction, a retriable provider error - and never given back. Twenty transient blips spread over four hours, each one recovered from and each one followed by real work, left a healthy run with no budget at all, and the twenty-first ended it. That is an accumulating debt, not a signal: a recovery that worked is not evidence of anything. The bound now asks the only question it was ever meant to - can this run get going again - and zeroes the moment a turn comes back whole, exactly as the empty-turn and cycle counters already did. The reset sits below the truncation check, so a run of truncations is still bounded while a truncation an hour ago no longer counts against a provider blip now.

  A second bound was needed to make that safe, and it is the one worth configuring: **`agent.max_recoveries` (default 200)** caps recoveries across a whole run however they are spaced. Where `max_continuations` catches a provider refusing *right now*, this catches the shape it cannot see - one that answers just often enough to keep resetting the consecutive count while the run spends its life retrying rather than working. Every good turn says the upstream is fine and only the tally says otherwise, so the tally has to be able to end the run. Deliberately absolute rather than a multiple of `max_continuations`: tying them together would mean that lowering the consecutive bound - the obvious thing to want, to fail fast on a stuck provider - silently lowered this one into a range a long healthy run reaches, reintroducing the accumulating budget above. `agent.Summary.Continuations` now reports the run's lifetime total rather than the consecutive count, since what a run *spent* is the useful number and the consecutive one is 0 at the end of any run that finished.

- **An order that keeps not concluding starts clean.** An unfinished run is continued automatically, which is right when the last attempt was interrupted and wrong once the transcript itself is what keeps failing - and nothing told the two apart, because a run that errors is neither `settled` nor `failed` and so stayed resumable forever. On a schedule that becomes a ratchet: each run resumes a longer, more damaged conversation, gets less far, and hands an even longer one to the next. zot now walks the `resumedFrom` chain and starts fresh past three unconcluded continuations, saying so on stderr. It is a losing streak rather than a lifetime count - a run that concludes ends the chain, so a long history of successful runs never makes the next interruption unresumable - and a predecessor the session directory cannot see ends the walk at what is known rather than assuming the worst.

### Fixed

- **A stalled upstream is retried instead of ending the run.** `Upstream idle timeout exceeded` - OpenRouter's wording for a provider that stopped emitting tokens - was classified as permanent and killed the run outright, with no retry and no backoff: the textbook transient, treated as a bad request. The status rule is why. It is authoritative in both directions, so a 4xx never retries whatever its message says, and gateways report a stall with whatever status they please. Two carve-outs now sit above it, both about time rather than the request: a message naming a stalled stream (`idle`/`stream`/`read`/`upstream` timeout, `timeout exceeded`, `X timed out`), and a 408. Kept narrow on purpose - a bare `timeout` is not enough, because `timeout must be a positive integer` is a rejected parameter and retrying it burns the budget the status rule exists to protect. Cost of the miss, in production: an unattended shift lost sixteen minutes of work and committed nothing, to an upstream that had merely gone quiet.


## [0.16.0] - 2026-08-22

### Changed

- **BREAKING: project context is read from `AGENTS.md`, not `AGENT.md`.** Every other agent that reads instructions out of a repository looks for `AGENTS.md`, and a project that already has one had to keep a second, near-identical file with a name only zot recognised - or, more often, wrote `AGENTS.md` and quietly got no project context at all, because a missing file is indistinguishable from an empty one. zot now looks for `AGENTS.md` in each context directory (the config directory, then the working directory), and only that name: `AGENT.md` is no longer read, so a stale one is ignored rather than silently competing with the file everything else uses. Skills are unchanged (`.skills/` or `skills/` in either location), as is the rule that the file augments the built-in instructions rather than replacing them. **Migration:** `git mv AGENT.md AGENTS.md` in each project, and rename `~/.config/zot/AGENT.md` if you keep global conventions there.

## [0.15.0] - 2026-08-22

### Changed

- **The default header stats are curated, and `tools` is no longer among them.** The bar shows the segments that fit and drops the rest, so every default costs the ones after it. A cumulative tool-call count climbs on every run and says nothing about whether this one is going well, so `tools` is now opt-in via `ui.stats`. `dir` moved to the end for the same reason - it never changes, and a static path is not worth the four live stats it was pushing off a 110-column terminal.

- **BREAKING: a ledger record now carries the run's evidence, not just its verdict.** A receipt that said only `reason: settled` asked to be trusted: to check the claim you had to find the `.jsonl` session log and read it. The run had already written everything needed - its own closing summary, the rounds and tool calls it took - so the receipt was throwing away proof it had been handed. `Record` gains an `evidence` block carrying the session id it was read from, the engine's own stop reason (alongside the ledger's), the run's closing summary, and its iteration and call counts. Nothing is computed: every field is copied from the result record the run wrote, which is what keeps it evidence rather than zot vouching for zot. Receipts stay honest when there is nothing to show - a run with no session log, an unreadable one, or one cut off before it recorded an outcome writes `missing:` saying which, rather than an empty block that reads like a run that did nothing. `Satisfied` is unchanged: only a `settled` record of the exact order content counts, and an unsettled run's receipt still keeps its evidence, because the ledger is a history rather than a list of successes. `Ledger.Record` takes the evidence as a final argument; existing receipts parse fine and simply carry no evidence block.

- **BREAKING: `zot` runs your project's book, and the book moved to `.zot/`.** Three problems, one shape. Orders could be read from anywhere but their receipts could not: `RecordRun` derived the ledger from the order file's own path (`<book>/orders/x.yaml` recorded to `<book>/records/x/`), so a brief that lived in a shared folder, a read-only checkout or a temp file wrote its receipt into somebody else's tree - or had nowhere to write at all. Both halves also claimed generic top-level names in the root of somebody else's project. And every invocation had to name the order files again, which made the book a filing cabinet rather than a queue.

  - **The book is one dotted directory.** `zot new` scaffolds to `.zot/orders/<slug>.yaml`, a successful run records to `.zot/records/<slug>/<run>.yaml`. **Migration:** `mkdir -p .zot && git mv orders records .zot/` - a ledger left at the old path is not consulted, so settled orders under it will run again.
  - **Both halves are configurable.** `internal/order` now exposes `Ledger{Root}` with `Record`/`Satisfied` methods and `recordsDir()` is gone; the CLI plumbs `--records-dir` through to it, defaulting to `<dir>/.zot/records` - the book of the project being worked on, not one beside whatever order file was named, because the receipt belongs with the work rather than with the brief. `--orders-dir` moves the other half: where `zot new` files an order, and where zot looks for work when you name none.
  - **A bare `zot` runs the book.** With no order paths it runs every `*.yaml` in the orders directory, in filename order, and the ledger decides which are still outstanding - so writing an order and typing `zot` is the whole loop, re-runnable with no queue to drain. With nothing to run it says how to write an order instead of exiting quietly. Naming order files still runs exactly those, read from any path in any tree.
  - **A bare `zot --watch` watches it.** `--watch` is now a boolean taking its target from the positional slot, so `zot --watch` watches the orders directory, `zot --watch ~/inbox` or `zot --watch "~/inbox/*.yaml"` watches that instead, and two targets are refused. The old `--watch=<target>` spelling is gone.

- **The agent is told, in terms it cannot lose, that no one can answer it - and a custom prompt no longer drops that.** zot has no input channel: a run is a work order, a provider and a read-only viewer. An agent that asks a question or waits for approval is not answered tersely, it is not answered at all - it burns its budget until a guard kills the run, and the work it never wrote is lost. The built-in prompt now carries an explicit non-interactive contract: nothing addressed to the user is delivered, never stop for input, approval, permission or confirmation, never end a turn with a question or an offer, decide ambiguity the way a careful engineer would and record the assumption with `progress` instead of asking, and end only by calling `success` or `failure`. The contract is a separate half of the prompt and is re-attached to whatever instructions a run resolves to, so setting `agent.instructions:` replaces zot's prompt - as it always did - without silently opting the run into an interactivity it does not have; instructions that already carry the contract (the defaults, or the defaults plus an `AGENT.md`) are left alone, so it is never repeated.

- **Unknown models are assumed to have a 1M-token context window** (was 128k), with a 64k output reserve (was a quarter of the window). The failure modes are asymmetric in practice: assuming too small compacts a long run over and over, summarising history the model could have kept, while assuming too large is recovered reactively - a provider's context-length rejection lowers the budget to what the error stated, and the operator can pin the real ceiling per model with `context:` in the config. Frontier models the catalogue has not heard of are the ones most likely to carry windows this large.

### Added

- **Header stats for how the run is going: `task`, `order`, `tps`, `pace`.** The bar counted things that had happened - iterations, tool calls, tokens - but nothing that answered "is this going well, and how much is left". `task` shows plan steps completed against planned, read off the agent's own `plan` and `progress` calls (a replan resets it, since progress against an abandoned plan is not progress; a model that outgrows its plan is followed rather than contradicted). `order` shows position in a batch - `2/5` - so a long queue reports how much of itself is left. `tps` is output tokens per second and `pace` is average wall time per iteration: the first says whether the provider is keeping up, the second is what actually predicts when a long run finishes. A stat with nothing to report yet shows `-` rather than `0`, because zero is a measurement and this is the absence of one. All four are configurable through `ui.stats` like any other.

- **Drafted orders are named by their title.** `zot new --draft` slugged the objective, so a folder of orders read `the-new-command-should-have-an-interactive-versi.yaml` next to `the-tui-should-have-task-status-progress-enabled.yaml` - names that are hard to tell apart in the one place orders are actually browsed. The drafting survey already proposes a title; the file now takes its name from it (`interactive-zot-new.yaml`), falling back to the objective when there is no title. Collisions are still uniquified rather than overwritten.

- **Work orders can carry a title, and the viewer prefers it.** The header showed the task - the whole order rendered for the model, objective plus criteria plus constraints - truncated to one line, so what named the run on screen was a paragraph cut mid-word. An order may now declare `title:`, an optional short label for people that never reaches the model (the objective is the contract; a title is how a human recognises it). Without one the file name becomes the title - `fix-the-flaky-test.yaml` reads "Fix the flaky test", dashes and underscores as spaces, sentence case rather than Title Case because an objective-derived name is a sentence. `zot new` scaffolds a commented stub, and the drafting survey is now asked to propose a title and writes it into the file. An order that was never a file gets no title rather than an invented one. Plain mode prints the title *and* the brief beneath it: a transcript is read after the fact, where losing what was asked for costs more than a long header does.

- **Watch mode: `zot --watch <folder-or-glob>` runs orders as they arrive.** A batch ends when its last order does, which made zot a thing you invoke rather than a factory you leave running: someone had to re-run the shell loop to feed it the next order. `--watch` takes a folder (`zot --watch orders`) or a glob (`zot --watch "orders/*.yaml"`, resolved like an order path against the invoking directory) and keeps the process up, sweeping the target every second and running every `*.yaml` work order it finds - including ones already sitting there at startup - as its own independent run with its own session log and ledger record, one at a time in filename order. The batch semantics carry over whole: a satisfied order is skipped (so pointing a watch at yesterday's folder picks up only what never finished), an unfinished run continues automatically, editing an order re-queues it via the content hash, and an order that fails is reported - named on stderr with "staying on watch" - without ending the watch or being silently retried; fixing the file is what re-queues it. A target that does not exist yet is reported once and kept under watch, so `zot --watch orders` before anyone creates `orders/` works. The engine is reachable as `internal/watch` with an injected dispatcher, so the watching itself is testable without a provider; Ctrl-C/SIGTERM stops watching cleanly.

- **An unfinished order continues automatically.** Running an order whose most recent session did not conclude - killed, crashed, aborted, or stopped by a guard - resumes that session instead of starting over: the order is the contract, and abandoning half its work because nobody typed `--resume` wastes everything the earlier run learned. Only a concluded run ends the story: settled means the ledger skips the order, and a declared failure is a conclusion, not an interruption, so it starts fresh. `--fresh` forces a clean start regardless; explicit `--resume <id>` still works for picking a specific session.
- **The order ledger: a finished order stays finished.** Restarting `zot orders/*.yaml` re-executed orders that had already completed, because nothing recorded doneness - and mutating or deleting the order file to track it would destroy the contract being tracked. A successful run now writes a record to `records/<slug>/<run-id>.yaml` beside `orders/`, carrying the run id, outcome, and a hash of the order content; an order with a settled record of its exact content is skipped on the next invocation, with the skip explained. Doneness is derived, never stored on the order: editing the order changes its hash and re-queues it (re-queueing is a diff, like everything in the book), a failed or aborted run leaves no record and runs again, and `--rerun` forces a run regardless. This is the level-0 ledger from the order-factory architecture - the same records a future zotd commits to the book.

- **Reasoning continuity for chat-completions gateways (`reasoning_details`).** A reasoning model interleaves its thinking with its tool calls, and OpenRouter carries that thinking as structured `reasoning_details` blocks that must be echoed back on the assistant message between tool steps. zot dropped them entirely - assistant replays carried only the tool calls - so a reasoning model lost its own thinking on every tool round, and some upstreams reject the request outright once the reasoning chain has grown: the diagnosed cause of the stealth-model 400s that worked "up to a point", and the same defect open against opencode, Roo-Code, VS Code and Home Assistant. The chat transport now reassembles the streamed blocks (merging text fragments, passing encrypted and summary blocks through untouched - the sequence is opaque and must not be modified) and the loop replays them verbatim on the turn's first call, exactly as reasoning items already flow on the Responses transport. The session log now also persists reasoning state (items and details both) on activities, closing a pre-existing hole where a resumed reasoning run replayed its calls stripped of the thinking that produced them.

- **The `read` tool requires a line range.** `startLine` and `endLine` are now mandatory, and a read without them fails - an optional range invited the model to read whole files, and a single large file (a 40KB test file, in the failure that surfaced this) can overflow a small context window and be rejected wholesale. Reads come back line-numbered with a header stating the file's total length, so the model can target a precise next range. This keeps every read bounded by construction rather than relying on a truncation backstop.
- **A configurable tool-output ceiling.** `agent.max_tool_output` (default 100000 bytes) caps a single tool result before truncation. Lower it for a model served by an endpoint with a small context window, where one large result can overflow the whole request. The ceiling is carried by the tool set rather than a package constant, so it varies per run.
- **A developer build dumps the exact refused exchange.** An opaque upstream 400 ("Provider returned error: ERROR") is only diagnosable from the request that provoked it, which no log kept. A `make dev` build (or `-tags dev`) now writes `<session>.failure.json` next to the session log on a provider refusal, carrying the status, the request that was refused, and the response that came back. It is gated on the build for the same reason `.env` loading is: the request body is the whole prompt, and a released binary must not spill it to disk beside every failed run - the session record keeps only the bounded response, and the full request lives solely in the dev dump.
- **A per-model `context` override.** A model the catalogue has not heard of is assumed to have a large window, so a serving endpoint whose real ceiling is smaller rejects the request before compaction ever fires - and an endpoint that reports overflow opaquely (a stealth model's bare "ERROR") gives the reactive recovery nothing to detect, so the run retries the same oversized request until its budget dies. Six consecutive production failures clustered in a 13KB band of conversation size diagnosed exactly this. `providers.<name>.models.<model>.context: 32000` declares the endpoint's real window; budgeting respects it, compaction fires inside it, and the run survives on the model instead of dying at a wall the error never named.

### Fixed

- **The `dir` stat keeps the end of the path instead of the start.** It was truncated like any other text, so `/workspaces/monorepo-zot/repos/zot/tool` showed as `/workspaces/monorepo-zot/repos/z…` - every column spent on the part shared by every project on the machine, with the one word naming this one cut off. It now drops whole leading segments and marks the cut at the front: `…/repos/zot/tool`. Segments are kept whole, because half a directory name is not a directory name; only a final segment that cannot fit on its own is cut, and then from the left so the end of the name survives.

- **A failed `--draft` no longer throws away your objective.** `zot new --draft` wrote nothing when the drafting survey failed - a provider 404, a flaky model - on the reasoning that handing back a plain scaffold would hide that the criteria were never drafted. But drafting is the optional half: the objective is the part only the operator can write, and it was the one thing not recoverable. A failed draft now scaffolds the objective anyway, prints where it went, and still exits with the drafting error naming that path - loud about the failure, without charging for it in lost work.

- **A stat segment in the header is shown whole or not at all.** The meta bar was clipped to the terminal width, which left whichever segment straddled the edge half-rendered - `elap`, `tok`, a count cut off mid-number. A truncated number is worse than an absent one because it can be misread, and the effect read as a broken UI rather than a narrow terminal. The bar now takes segments in the configured order for as long as they fit whole and stops at the first that does not, so what is on screen is always a prefix of the configured stats that grows and shrinks predictably as the terminal is resized. A terminal too narrow for even the first segment draws an empty bar rather than a fragment.

- **A deliberate stop reads as one.** Quitting the viewer mid-run (q or Ctrl-C) surfaced as "agent run ended before completion" and, in a batch, "order X stopped the batch: …" - a mysterious failure report for a keypress. The cancellation is now a distinct sentinel reported as what it is: "batch stopped: run cancelled - the viewer was closed while the run was still going."
- **A batch no longer stalls on each finished order's held screen.** The viewer holds a run's final screen until q - right for a single order, but in a batch it meant every completed order waited for a keypress nobody unattended would make before the next could start. Intermediate orders now close their viewer on completion and the batch advances; the last order holds for review as before. Session logs carry each order's full record either way.
- **Usage events in the session log carry their numbers.** They were recorded as bare `{"kind":"usage"}` - the token counts lived in fields the recorder interface does not have - so "why did this run cost 567k tokens" was unanswerable from the log. The counts are rendered into the event text ("input 25914 output 1176").
- **The loop's corrective nudges are visible.** An empty turn, a truncated answer being continued, and a settle reminder each injected their nudge silently - a live provider held a stream for three minutes, returned nothing, was nudged back to life, and the viewer showed two bare iteration dividers indistinguishable from a hang. Each nudge now emits a notice ("the model returned an empty turn; nudging it to continue (1/3)") rendered in the viewer and the plain stream, and recorded in the session log.
- **Compaction now fires before trimming turns lossy, ending the re-reading loop.** The compact trigger was driven by the provider's reported prompt count - which measures the previous request AFTER the thread builder trimmed it to fit, so it sat below the trigger forever while the trimmer silently dropped ever more history. The model re-read what it lost (a live run read the same file sections three times over), the conversation grew, more was trimmed - a loop that burned the run's budget on amnesia while compaction, the mechanism built for exactly this, never fired once. The trigger now takes whichever is larger: the reported count (real usage, catching what the estimate misses) or the local estimate of the whole conversation (the same measure the trimmer applies, firing compaction before history is silently destroyed).
- **A trimmed thread no longer loses its only user turn - the diagnosed cause of the stealth-model 400s.** The thread builder keeps the largest suffix of the conversation that fits, so the first message trimmed is the oldest: the run's opening user message. From that iteration on every request was `system + assistant/tool` with no user turn at all, which strict providers reject wholesale - deterministically, with an opaque 400, at whatever byte size the trim happened to fire. Bisected live against the refused request itself: the identical 120KB request with a single user message injected was accepted. The request builder now guarantees a user turn - when trimming has dropped the opener, a stand-in pointing at the instructions is inserted after the system prompt. The objective was never at risk (it lives in the instructions precisely because user messages are trimmable); what had to be restored was the user turn's existence.
- **Quitting the viewer no longer loses the run's outcome.** Pressing q cancels the run, and the engine then records its aborted ending into the session log - but the viewer returned the moment the program did, racing that record against the caller's session-writer close, so a quit run was logged as "running/interrupted" forever with no outcome at all. The viewer now waits (bounded) for the engine to conclude before returning. And a cancellation that lands mid-call was recorded as the provider error it caused - "the provider failed" for a user pressing q - because the abort check only ran at the top of the loop; the error path now recognises a cancelled context and records the abort it is.
- **Retries are visible, and they no longer spend the iteration budget.** A retried provider failure emitted its event into the void - neither the viewer nor the plain stream rendered it - so a run surviving an outage showed empty iteration dividers stacking up, indistinguishable from a hang. Both renderers now show "↻ retrying" with the error. And each retry looped back through the top of the loop, charging the iteration budget for a model call that never became a round - twenty spaced retries through an outage cost twenty iterations of work the run never got. A failed call now refunds its iteration; continuations alone bound recovery, as the guards always documented.
- **A flaky upstream behind a gateway no longer kills a run.** OpenRouter reports an upstream provider's failure as a 400 "Provider returned error", which the retry classification read as a request defect - so an intermittent upstream hiccup (stealth endpoints especially) ended a run outright with its whole continuation budget unspent, at varying iterations and request sizes, exactly the death the wire evidence diagnosed. A gateway-wrapped upstream failure is now retriable whatever status the gateway put on the envelope - it is a 502 in a 400 costume - while a plain 400 remains the request defect it is. A wrapped context overflow is not lost to the retry loop: the loop checks context-limit detection first, and the upstream's raw body is folded into the error message where those patterns match.
- **The failure dump is written the instant a failure happens, not at the run's end.** A developer build persisted the failing exchange only when the run concluded, so a kill or crash mid-retry - the very case the dump exists for - reached that end and found nothing. The provider failure now flows through the event stream and is dumped to disk the moment each retry fails, superseding the previous one; the dump reflects the latest failure at all times, whatever ends the process. This makes the earlier abort-preservation fix belt-and-suspenders rather than the only path.
- **A stopped run keeps the failure it was stopped over.** Quitting during a retry storm recorded `aborted / "context canceled"` and discarded the provider failure that was in flight - so the developer dump, whose whole purpose is to capture that exchange, never wrote, because the operator quit precisely to go and read it. The run now remembers the last provider failure and carries it into the abort record, so the dump is written even though the ending is an abort rather than a provider error. A clean cancellation with no failure behind it still records a bare abort.
- **A signal records an outcome instead of killing the process silently.** The CLI ran under a background context with no signal handling, so a `kill`/SIGTERM (or a supervisor stopping the process) left the session with no ending at all. SIGINT and SIGTERM now cancel the run, letting the engine record its aborted outcome - and dump any in-flight failure - before exit. SIGKILL remains uncatchable; the incrementally-written conversation is the record there.
- **A provider refusal's wire evidence is recorded in the session.** The result record gains a `failure` object carrying the HTTP status, the raw (bounded) response body, and the size of the request that was refused. Error text says what the loop concluded; the wire evidence is what troubleshooting needs - an upstream that answers an opaque "ERROR" and one that names a context overflow read the same in prose, but the refused request's byte size against a suspected context ceiling is the difference between a correlation and a diagnosis.
- **A gateway-wrapped provider failure now names its upstream cause.** OpenRouter reports an upstream failure as `Provider returned error (400)` with the actual diagnosis - the upstream body and which provider produced it - in the error's `metadata`, which the parser dropped. The wrapped body (bounded) and upstream name are now appended, so a run's failure reads "Provider returned error: This model's maximum context length is … (upstream: …)" instead of a shrug.
- **A provider failure's actual error is no longer lost.** A run that died to a provider error showed "the provider failed" in the viewer and recorded the same six words in the session log, while the provider's own diagnostic - the 404 naming the wrong model, say - was dropped on the floor: the viewer ignored the terminal error because the exit event had already flipped the run's status, and the session record had no field for it. The viewer now keeps and shows the underlying error (and returns it to the CLI, so the process exits with the real message), and the session log records it in the result's new `error` field - a run nobody watched is answerable again. A late error still cannot resurrect a run that ended in success.
- **`zot new` with `--provider` or `--model` but without `--draft` is refused** instead of silently ignoring the flags and scaffolding a plain order - whoever typed a model expected the drafting survey to start, and the error now says the missing word.

- **The model catalogue now starts at GPT-5, and token budgeting is provider-neutral.** GPT-4, GPT-4o, GPT-4.1, GPT-4.5 and GPT-3.5 are no longer offered: they are legacy, largely unsupported choices for an agentic coding harness. ## [0.13.0] - 2026-08-20

### Added

- **`zot new` scaffolds at three levels of help.** Bare `zot new` writes the blank order form (which refuses to run until its objective is filled in), `zot new "objective"` fills the objective in, and `zot new --draft "objective"` additionally has the configured model propose the acceptance criteria and constraints - written into the file as real YAML for the operator to edit, because the model only ever drafts; the operator's review is what makes the criteria a contract. The draft is not a blind call: it runs as a small autonomous run through the same engine as real work, with a read-only toolbox (`read` and `list` - a survey that can edit files or run commands is not a survey), so the proposed criteria are grounded in the actual working tree - its build files, its test setup - and it delivers the draft the way every run ends, through the success tool. The survey renders in the same viewer as any run - watching a run work is zot's whole interface, and a draft that worked in silence read as a hang - and the viewer closes itself when the survey ends (`tui.Meta.QuitOnDone`), because the draft's deliverable is the scaffolded file, not a held final screen waiting on a keypress. The draft travels as plain bulleted lines rather than YAML - a natural criterion quotes the command it names (`"go test ./..." exits 0`), which is prose to a YAML parser, and real drafts died on exactly that; line-based parsing has no quoting rules to violate, and the scaffold re-encodes the lines as proper YAML. Prose and code fences around the lists are tolerated, and a draft with no recognisable criteria fails with an excerpt of what the model actually returned. It leaves no session log and fails fast on provider trouble rather than sitting out an outage, and a failed draft writes nothing rather than silently handing back the plain scaffold. `--draft` takes `--config`, `--provider` and `--model`, so a cheap model can do the drafting.

### Changed

- **zot takes work orders, not prompts.** The command line no longer accepts a prose task: `--task`, `--task-file` and the positional plain-English brief are gone, and zot's only input is one or more work order files - small YAML documents carrying the durable `objective`, the `acceptance` criteria that define "done", and the `constraints` the work must hold to. `zot new "the objective"` scaffolds one under `./orders`, and typing prose where an order belongs gets an error that teaches the new shape. The two-step flow is deliberate: the pause between writing the order and running it is where acceptance criteria get written, and the acceptance list is the contract a future verification gate will judge the result against. `zot orders/*.yaml` runs a batch - each order is its own run with its own session log and recorded outcome, in sequence, stopping at the first order that does not end in success, because later orders usually assume the earlier ones landed.
- **A resume is "keep going", never "start over".** `--resume` no longer takes follow-up text or a replacement objective - it continues the order its session was started with, and orders passed alongside it are rejected rather than silently blurring which outcome belongs to which order. A resumed run also opens with a continuation kickoff that tells the agent to reconcile its plan with the current tree, instead of the fresh-start kickoff that told an agent with half the work done to begin again.
- **`tui.Run` returns the run's recorded outcome alongside any error.** The viewer rendered a run's ending but only handed callers errors, so a caller whose deliverable IS the recorded outcome - the draft run reading criteria out of the success summary - had no way to receive it. `Run` (and the stream/viewer paths beneath it) now return an `Outcome{Reason, Message}`; embedders that call `tui.Run` add the extra return.
- **zotui dispatches missions as work orders.** The sandbox no longer receives the mission as command-line prose: the dispatcher renders it to order YAML (a mission that already is an order document passes through intact, so the worker form can carry acceptance criteria), writes it into the sandbox through the environment - which, unlike shell interpolation, carries arbitrary text without quoting rules getting a say - and invokes the worker on that file.

## [0.12.0] - 2026-08-19

### Security

- **zotui now refuses requests aimed at it from another site.** Binding to loopback controls where the listener can be reached from, not which pages may drive it: a site the operator visits can rebind its own hostname to `127.0.0.1` and, from inside the browser, become same-origin with the command center - enough to read `/api/state` and launch runs, which is arbitrary code execution on the configured compute. The server now requires the `Host` header to name the address it actually serves, rejects state-changing requests the browser marks cross-site or whose `Origin` disagrees with their `Host`, and requires a JSON content type where a request carries a body (worker create and update), so a cross-site HTML form cannot create or reconfigure a worker; the bodyless state-changing routes rely on the cross-site checks. The host check stays on under a wildcard bind - a container must bind `0.0.0.0` to publish a port, which says nothing about which names may drive it; an operator who genuinely serves zotui by name lists it in `ZOTUI_ALLOWED_HOSTS`, or sets `*` to make being reachable by any name the explicit decision it should be.
- **A provider with a custom `base_url` no longer inherits its built-in API key.** The documented rule was never enforced, so pointing a provider at a proxy - or at a typo - silently forwarded the ambient `OPENAI_API_KEY` (or equivalent) to that host as a bearer token. A custom endpoint must now carry an explicit `api_key`; the loopback waiver for local proxies is unchanged.
- **zotui destroys in-flight sandboxes on shutdown.** Run contexts were detached from the process signal context, so Ctrl-C killed the dispatch goroutines before their cleanup ran, leaving orphaned containers executing with an injected `GH_TOKEN` and run rows stuck in `running` forever. Shutdown now cancels active runs and waits for their sandboxes to be destroyed, and startup reconciles runs an earlier process left in flight.

### Fixed

- **A rate limit no longer kills a run.** 429 is deliberately excluded from the retriable set because it needs the provider's own schedule rather than a tight retry loop - but nothing implemented that schedule, so a single throttle response ended the run outright with its whole continuation budget unspent. The loop now reads `Retry-After` (both the seconds and HTTP-date forms) and waits it out, capped so a mistaken or hostile header cannot park an unattended run for hours. The advised wait is floored by the retry backoff, so a provider sending `Retry-After: 0` on every 429 cannot re-create the tight loop, and a delta-seconds value large enough to overflow saturates instead of wrapping negative and skipping the wait entirely.
- **Retriable provider failures are now spaced out.** They were retried with no delay at all, so an outage burned all twenty continuations in under a second - a run died to a blip a short pause would have outlived, while hammering an endpoint that was already failing. Retries now back off exponentially from one second, capped at thirty. The escalation counts consecutive failures and resets after a successful turn, so a blip late in a long run pays the base delay rather than whatever ceiling earlier, unrelated retries had ratcheted up to.
- **An agent-declared failure is no longer reported as success.** The `success` and `failure` tools both ended a run as "settled", which exits 0 and renders as a green "done", so a mission the model gave up on was indistinguishable from a finished one to scripts, schedules, and the session log. `failure` now has its own stop reason, exits non-zero, and renders as a declared outcome rather than as a process-level crash, in the interactive viewer and plain output both.
- **Reasoning models can complete tool calls again.** The Responses transport asks for encrypted reasoning state with `store: false`, which makes the streamed copy the only one there is - but nothing captured or replayed it, so the second request of every tool round replayed a `function_call` without its required reasoning item and was rejected outright. The state is now carried out of the stream, across the turn boundary, and replayed ahead of the calls it produced.
- **A long streaming turn is no longer cut off mid-answer.** The client's ten-minute timeout bounded the whole exchange including the response body, so a reasoning model that thought and then streamed a long answer was killed while actively producing tokens - and the resulting error matched no retriable pattern, so the run stopped. Connect and response-header time are bounded instead, with a separate idle timeout that fires only when a stream genuinely goes silent. Error responses share the same stall discipline: a server that sends a `500` header and then holds the body open surfaces a bounded error instead of parking the turn forever.
- **A stream that ends without a terminal frame is now an error rather than a short answer.** An intermediary that cleanly closed a chunked response mid-generation produced a truncated turn that the loop recorded as the model's complete answer. Both transports now require an explicit terminal frame and surface a retriable error without one.
- **Compaction is no longer repeated after a failed turn.** An error carries no token usage of its own, so the pre-compaction reading survived a failure and made the next iteration compact the already-compacted thread again - once per retry, condensing summaries into summaries during a transient outage.
- **The conversation is recorded as the run goes.** The session log promises that a crashed run leaves everything up to the crash, but the conversation was written only once the run had ended, so a run killed at iteration 500 left the brief and nothing else and `--resume` restarted the task from scratch. It is now written at each iteration boundary, with the existing reset handling the history rewrite that compaction performs.
- **An abandoned stream is cancelled.** The runaway guard ends a turn while the provider is still streaming; the transport's producer goroutine was left parked on a send nobody would receive, holding its HTTP response body open for the life of the process, and leaked one per trip of the guard. Cancellation also no longer races the stream's terminal error out of existence: a turn cancelled mid-stream always surfaces its error instead of sometimes reading as a short, complete answer - which could let an interrupted compaction record a truncated summary as a valid checkpoint. The agent's own event channel got the same treatment, so an embedder that cancels a run and stops draining events cannot park the run goroutine forever.
- **An explicit `--max-iterations` now beats a per-model cap**, instead of the config file silently overriding the command line, and the viewer's iteration denominator shows the limit the engine actually enforces.
- **`zot --resume last` with no new task no longer prints the usage block** before resuming.
- **Quitting the viewer stops the agent** rather than only stopping watching it - it holds shell and file-write access, so an embedding process was left with something editing the working tree and nothing on screen reporting it.
- **zotui keeps a failed run's exit code.** Two status writes raced on the failure path and the second erased the code, so every failed run recorded a null exit code.
- **zotui run output no longer grows quadratically.** Output was appended by rewriting the entire accumulated column, and the browser re-fetched the whole buffer every 1.5 seconds. Output is now stored in chunks, capped to a tail window, and served incrementally from an offset.
- **zotui no longer mis-records a run that failed as paused**, and concurrent resumes of the same run can no longer launch two sandboxes.
- **A failed output poll no longer wipes the zotui terminal.** The poller's offset had already advanced past everything on screen, so one transient fetch error blanked the log and recovery rendered only bytes appended after the blip. The rendered output now stays put, the stall is noted in the tail indicator, and the next poll retries from the same offset.
- **Truncated text no longer splits UTF-8 runes.** A task, tool argument, or session listing in CJK or emoji rendered a replacement character, and the cap counted bytes rather than characters, so lines were cut far short of the width they were given.
- **Cloudflare AI Gateway connections now list the whole model catalogue.** Cloudflare routes creator-qualified model names exactly as OpenRouter and Vercel do, but the catalogue treated it as a direct provider that originates models of its own - so a Cloudflare connection resolved to an empty model list, and config validation rejected every model the gateway can actually serve.
- **`kimi-k2.5` is catalogued with a 262,144-token context window**, correcting a transposed 262,114 that budgeted the model 30 tokens short of its window.
- **A loopback `base_url` written as bracketed IPv6 without a port** (`http://[::1]/v1`) is now recognised, instead of being rejected as insecure and denied the local-endpoint API-key waiver.
- **An `edit` tool renders a header naming the file** instead of dumping both whole versions of it inline, directly above the diff that renders them properly.

### Added

- **The GitHub update check is wired up.** It was complete, tested, and called from nowhere while three documents described it as live behaviour. Release builds now check once per run, off the critical path, silent on any failure, and report to stderr; development builds still skip it entirely.
- **`RetryBackoff`** on the agent and loop options, for callers that need to tune - or, in a test driving an outage, disable - the pause between retries.
- **`ZOTUI_ALLOWED_HOSTS`** - a comma-separated list of additional host names zotui accepts requests for (entries are case-insensitive), with `*` disabling the host check outright. Replaces the implicit waiver a wildcard bind used to trigger.

### Changed

- **Breaking: the Responses transport rejects `Request.Stop` instead of ignoring it.** The Responses API has no stop-sequence parameter, and the transport is selected automatically for OpenAI reasoning models, so a caller that set stop sequences silently got unbounded generation.
- **Breaking (`zotui` HTTP API): `GET /api/runs/{id}/output` takes an `?offset=` and returns only the bytes after it**, with `X-Output-Start` and `X-Output-Next` headers. Worker create and update now require a JSON content type.
- **Breaking (`zotui`): a wildcard bind no longer disables the `Host` allowlist.** A deployment that relied on `0.0.0.0` implying any-host access must now name its hosts in `ZOTUI_ALLOWED_HOSTS`, or set it to `*` to opt out explicitly.
- **Breaking (`zotui` database): migration 4 replaces the `runs.output` column with a `run_output` chunk table.** Output accumulated by an earlier build is discarded, and run output is now capped to an 8 MiB tail per run.

## [0.11.0] - 2026-08-18

### Added

- **Local Docker compute for zotui.** `compute.type: docker` creates an ephemeral container with its own isolated `/workspace`; remote repositories are cloned inside it, while a configured local checkout is transferred as a Git bundle and cloned rather than mounted. Zotui streams the run output and removes the container even after cancellation.
- **Vercel Sandbox compute for zotui.** `compute.type: vercel` creates a non-persistent Vercel Sandbox using its built-in runtime or an optional project VCR image, checks out the selected remote Git repository using any credential minted by its repo connection, installs the embedded Zot worker and model configuration privately, streams raw ANSI output, and stops the sandbox after the run. An explicitly listed public GitHub repo can be used without App credentials for a credential-free smoke test.
- **A repository development container for Go and zotui work.** It pins the project toolchain, runs as a non-root developer, provides Git with Git LFS and Docker-in-Docker, persists Go caches, Docker data, and zotui state in named volumes, forwards the command-center port, builds the embedded Linux worker artifacts, and includes a credential-free fixture configuration. `make dev-ui` provides the same local workflow outside the container.
- **GitHub App repository connections for zotui.** An App ID, installation ID, and PEM private key are enough for the command center to discover an installation's repositories and mint a fresh token restricted to the selected repository for each run. The private key stays on the host; remote compute receives only the short-lived clone credential and `GH_TOKEN`.
- **Self-deploying Zot workers.** Zotui embeds release-mode Linux amd64 and arm64 Zot executables, selects the compute platform, and installs the matching binary into each Docker or Vercel sandbox alongside its private runtime configuration. Environment images now provide only toolchains and project dependencies; they no longer need a Zot-specific base image.

### Changed

- **The unfinished Cloudflare compute seam has been removed from ZotUI.** Cloudflare Sandbox requires a separately deployed Worker control plane rather than the direct account-token integration the stub implied, so `compute.type: cloudflare` and its unused credentials are no longer advertised or accepted. Cloudflare AI Gateway remains available as an independent model provider.
- **Breaking: model backends are now providers throughout Zot's user-facing surface.** Select one with `--provider`; configure `default_provider` and `providers`; and use `driver` when a named provider connection (such as `corporate`) needs to select a different implementation (such as `openai`). The old `--backend`, `default_backend`, `backends`, and nested `provider` spellings are removed rather than retained as aliases. The TUI stat and session metadata follow the same vocabulary (`provider` for the selected connection, `driver` for the resolved implementation), and ZotUI emits the new worker configuration.
- **ZotUI environments now have a standard runtime when `image` is omitted.** Local Docker and the repository Dev Container use the same pinned Microsoft Dev Containers Bookworm base. On Vercel, ZotUI omits both `image` and the legacy `runtime` property so the `/v4/sandboxes` endpoint selects Vercel's managed default image. All provide a shell, Git, and curl, and ZotUI deploys Zot separately. `image` remains an explicit compute-specific toolchain override; Vercel overrides must be a Vercel-managed image or reside in the configured project's VCR.
- **Breaking (`zotui` Docker compute): host bind mounts have been removed.** Every Docker run now owns an isolated checkout. Remote repositories are shallow-cloned with any short-lived credential delivered through stdin, and local repository connections clone a copied Git bundle containing committed refs. Agent writes can no longer modify the host checkout directly.
- **Provider-scoped model lists now work consistently across Zot and ZotUI.** A provider with no `models` uses Zot's built-in catalogue; an explicit `models` map replaces it with a custom alias/allowlist. In standalone Zot the list remains optional and an omitted list keeps accepting uncatalogued new models. **Breaking (`zotui` config):** models now live under their provider, environments name both `provider` and `model`, and workers/runs persist that pair. ZotUI requires every enabled provider to resolve to at least one custom or built-in model because the provider-first worker form is driven by that list. ZotUI's file remains independent from standalone Zot's config.
- **Breaking (`zotui`): the terminal command center is replaced by the browser software-factory UI.** Running `zotui` now serves the embedded web app on `127.0.0.1:8080` (override with `ZOTUI_ADDR`). Its backend models durable reusable workers, recurring schedules, and distinct run histories with controls and output, replacing the one-shot `jobs` table. Migration 2 removes that experimental table and its records.
- **Breaking (`zotui` config): repository connections are now `repos`, compute providers are `compute`, and an environment references `compute`.** The configuration now reads as the job path itself: repo + environment + model, with the environment binding compute to its image and variables. The old `sources`, `runners`, and `environments.*.runner` keys are removed rather than retained as aliases; unknown keys now fail during config loading instead of being silently ignored.
- **The CLI now uses GNU-style flags (`spf13/pflag`), matching rook and the rest of the ecosystem.** Long flags are double-dash (`--provider`, `--dir`), flags may appear **after** the positional task (`zot "do X" --plain` now works, where before the flag was folded into the task string), and `--help`'s flag list finally renders `--flag` to match the examples and the docs - the single-/double-dash mismatch the stdlib `flag` package produced is gone. **Breaking:** single-dash long flags (`-provider`) no longer parse - use `--provider`. zot has no short flags and every documented example already used `--`, so anything following the docs is unaffected.

### Fixed

- **Release builds now require Go 1.26.6.** The original 0.11.0 artifacts used Go 1.26.5, whose standard library has six vulnerabilities reachable from Zot; the corrected release is rebuilt with the patched toolchain.
- **Automatic releases now wait for CI to pass on the exact commit being tagged.** The release workflow independently verifies that successful CI run before publishing, so a version bump cannot publish binaries or a container from a commit that failed its vulnerability, test, coverage, or build gates.
- **The zotui worker form now presents repositories from the selected code source.** A sole configured repository is selected automatically, multiple repositories are offered as a dropdown, and connections without a fixed list retain an explicitly explained `owner/name` field instead of making every repository look like unvalidated free text.
- **The browser command center now has a product route at `/workers`.** `/` redirects there, while the mockup artifact path `/operations/instances.html` is no longer public.
- **New zotui workers now inherit zot's 1,000,000-iteration default.** The browser, application validation, and persistence path no longer carry conflicting 20-iteration scaffold fallbacks.

## [0.9.0] - 2026-08-06

### Added

- **The read-only viewer is a public, embeddable package: `github.com/openzot/openzot/tui`.** It moved out of `internal/`, so another tool can render the same terminal view over its own agent run. The seam is the public `agent` surface - a caller supplies its own `*agent.Client` and `agent.ExecuteWithToolsOptions` (its own tools, skills and instructions), and the viewer renders the `AgentEvent` stream; the engine binding lives in the embedding application, not the view.
- **Themeable brand colour via `tui.Theme`.** An embedder sets the view's accent and secondary; `tui.DefaultTheme()` is a neutral, near-monochrome identity so a host can own the colour. The semantic status colours (running / done / failed) and the diff gutters stay fixed, so their meaning reads the same in every application.
- **The header stats bar is configurable, and now shows token usage and limit progress.** `ui.stats` (or `tui.Meta.Stats`) chooses which fields show and in what order - any of `model`, `backend`, `dir`, `iter`, `tools`, `edits`, `elapsed`, `tokens` (default: all). The `tokens` field reports the **provider's own** cumulative token counts (`↑` prompt, `↓` completion) - the real billed usage, server-side prompt caching and all, never a local estimate - surfaced live on a new `agent.UsageEvent` and accumulated in the run's `Budget`. And `iter` / `tools` / `elapsed` show progress against a configured limit (`5/1000`, `00:12/30:00`) when one is set - the 1,000,000 iteration backstop is treated as "no limit" and shows none.

### Changed

- **zot's own viewer is now neutral** (a slate accent) rather than the previous purple/pink, so it stays out of the way and reads as the default rather than a brand.
- **The header meta bar colours each field by kind** - model and backend highlighted, tool and edit counts by meaning, paths and timing muted - with fixed functional hues (independent of the brand accent), so the header carries colour and stays scannable even under a neutral theme.

### Fixed

- **The viewer's scrollback is now bounded, and configurable.** It previously kept every log line for the whole run, so a long autonomous run (unbounded tool calls, up to a million iterations) grew the viewer's memory without limit and made each redraw re-process the entire history. The on-screen log is now capped at the most recent 5,000 lines by default - the full, untrimmed run is always in the session log on disk - and a marker points there once the log has been trimmed. Keep more (or less) on screen with `ui.scrollback` (or `ZOT_UI_SCROLLBACK`); embedders set `tui.Meta.MaxScrollback`.

## [0.8.0] - 2026-08-05

### Features

- **Vercel AI Gateway** is a built-in backend. `export AI_GATEWAY_API_KEY=... ; zot --backend vercel --model openai/gpt-4o "..."` - a fixed OpenAI-compatible endpoint fronting many providers, so it needs nothing but the key.
- **Cloudflare AI Gateway** is supported. Its endpoint carries your account and gateway ids, so there is no fixed URL to ship: configure it as a backend with `provider: cloudflare` and your gateway's compat URL. A run that omits the URL fails with an actionable error naming the shape to use, rather than a bare "unknown provider".
- **Bare model names are auto-qualified on gateways.** A gateway routes by a creator-qualified name (`z-ai/glm-5.2`), and each gateway spells the creator differently - OpenRouter wants `z-ai`, Vercel wants `zai`. You can now give the plain model (`--model glm-5.2`) and zot supplies the right prefix from its catalogue per gateway, because a model is the same model whichever gateway serves it. A name you qualify yourself is always sent as-is, and a model zot has not catalogued passes through bare for the gateway to resolve - zot never invents a prefix it cannot justify.
- **`plan` and `progress` tools.** The agent lays out an ordered plan with `plan` and narrates where it is with `progress` (done, current, blockers, next), and both are rendered in the viewer - so a run you are watching shows the plan it is following and how far along it is, not just a stream of tool calls. They are part of `agent.DefaultTools()`, so an embedder gets them too.
- **The task lives in the system prompt.** A run's objective is now held in the instructions rather than as the first user message, so it survives compaction - a long run cannot lose sight of what it was asked to do. `--task` / `--task-file` set that durable objective; a bare positional is promoted to it. Free-text passed alongside a task becomes an ordinary opening user message (a nudge, not the objective), and `--resume` inherits the task from the session and treats new text as the nudge.
- **Approaching-limit notices.** As a run nears a bounded limit - iterations, tool calls, or wall-clock time - the model is told, once at each of `limit_checkpoints` (default `[50, 80, 90]` percent), so it can pace itself and finish before the hard stop rather than being cut off mid-task. Each notice names which limit is approaching, in the units the model counts in, and its urgency scales with proximity: a heads-up to stay aware at the halfway mark, a nudge to prioritise as it nears, and finish-now only near the end - telling the model to wrap up at 50% would make it quit with half its budget unused. Set `limit_checkpoints: []` to turn them off.
- **The run's budgets are configurable, with matching `ZOT_AGENT_MAX_*` env overrides.** `max_settles` (how hard zot pushes the model to record an outcome), `max_calls`, `max_time`, `max_tokens`, and the `max_continuations` / `max_cycles` / `max_empties` safety guards can all be set in the config file or the environment, rather than being hard-coded. `max_time` is a wall-clock deadline checked at each step (`"30m"`, `"2h"`); `max_tokens` caps a single response.
- **Portable builds bake the configuration into the binary.** `go build -tags portable` embeds `internal/config/portable.yaml` (model, backend, even provider keys) into the executable, producing a self-contained artifact that runs with no config file and nothing to set at the destination. The baked layer is applied _last_ - above the config file and the environment - so what you compiled in is authoritative and the runtime environment cannot redirect it; fields you leave out still fall through, so you can pin the model and backend while taking the key from a `$VAR` reference. `zot --version` reports `portable config`, and the build fails loudly if the file is absent rather than shipping an unconfigured binary. The trade-off - a baked key is extractable, so the artifact becomes the secret - and the full recipe are in [docs/portable-config.md](docs/portable-config.md).
- **Configurable context-overflow strategy: `compact` (default) or `truncate`.** As the conversation approaches the model's window, `compact` now condenses the older history into a **checkpoint** with a real model call - so a long run keeps a condensed memory of its early turns rather than having them silently dropped - while `truncate` keeps the previous behaviour of trimming the oldest messages to fit. A checkpoint is pinned ahead of the conversation and never summarised again, so repeated compactions accumulate a chain of segment summaries rather than re-condensing earlier summaries into a lossy summary-of-a-summary (the mechanism the derived-from engine calls a checkpoint). Compaction is proactive and driven by the provider's reported input usage (the local estimate stands in only until the first turn reports): it fires once that usage crosses `compact_trigger_ratio` of the window and clears the `compact_min_tokens` / `compact_min_messages` floors. An outright provider rejection still falls back to the existing no-model structural summary (the request that was just rejected cannot be re-sent to a summariser), and a summariser outage degrades to that structural summary rather than stalling the run. Set via `agent.context_strategy` (or `ZOT_AGENT_CONTEXT_STRATEGY`); the trigger and floors are configurable. This ports the `thresholdStrategy` mechanism from the engine zot was derived from, which had not been carried over - only truncation had.

### Changed

- A prefixed model on a gateway resolves its real context window behind the prefix, so budgeting is sized to the actual model rather than the conservative default. (OpenRouter, already a backend, gains this along with the two new gateways.)
- **Tool calls, time, and output tokens are now unbounded by default; `max_iterations` is the only finite backstop.** A run should stop because it finished or went wrong, not because it hit an arbitrary tool-call ceiling mid-task - so `max_calls`, `max_time` and `max_tokens` impose no limit unless you set one, and 0.7.0's default tool-call budget of 1,000 is gone. The cycle, empty and continuation guards (which catch a run that has actually broken) still apply. Set any of the three explicitly to bound a run's cost or length.
- **The "factory model" table no longer claims a Verify stage the engine enforces.** Settle mode checks that the agent _declared_ an outcome, not that the work _is_ done - the agent verifies itself by running the tests because its instructions tell it to, and zot does not yet independently gate the outcome on a check of its own. The README said "Inspects results and iterates when the job is not complete" as though the engine did this; it now describes the run's real shape (the engine guarantees only the brief and the recorded outcome) and marks Verify as the agent's discipline, not an engine-enforced check.
- **A 90% test-coverage gate, enforced in CI and locally.** `make cover-check` and the CI **Coverage gate** step run one script (`scripts/coverage.sh`) that fails the build if total statement coverage drops below 90%, printing per-package numbers so a failure points at what shipped untested. A short `AGENTS.md` and an `.agents/skills/testing-and-coverage` skill record the conventions - tests assert behaviour, not constants, and are bite-checked against broken code.
- **The system prompt is configured as `instructions`.** It was `backstory`, a term carried over from a hosted product; for a tool that talks straight to any OpenAI-compatible provider, `instructions` is both the word that ecosystem's own APIs use and an accurate description of what the field holds - an operating spec, not a persona. The config key is `agent.instructions`, the env override `ZOT_AGENT_INSTRUCTIONS`, and the library surface `agent.Instructions` / `zot.DefaultInstructions`.

### Fixed

- **Loop-detection counted cumulative, not consecutive, repetitions.** The cycle budget never reset once a round came back clean, so two unrelated repetitions anywhere in a long run added up and could falsely stop it. It now zeroes on a non-cyclic round - counting consecutive cycles, as the engine zot was derived from does. (Surfaced by a parity audit against that engine.)
- **The context-trim estimate priced a tool call by its text alone**, which is empty for the request half - so an argument-heavy call (writing a big file) was counted as nearly free, letting a thread the estimate thought fit get rejected by the provider. The trimmer now counts the whole activity payload (name, arguments, result), matching the estimator used everywhere else.
- **An empty turn in settle mode now points the model at the terminal tools.** A turn producing nothing is still bounded tightly by the empty budget (a stuck model must not burn the whole settle budget on silence), but its nudge now names `_success` / `_failure` rather than telling the model it may simply "say it is finished" - which would not record the outcome settle mode requires.

## [0.7.0] - 2026-08-05

### Features

- **Native backends.** zot talks straight to a model provider over the OpenAI-compatible API, with the agentic engine running inside the binary. There is no hosted engine and no gateway in between: all you need is a provider key, and nothing leaves the machine except the request to the provider you configured. Fourteen backends ship built in - `openai`, `anthropic`, `groq`, `mistral`, `deepseek`, `openrouter`, `together`, `cerebras`, `xai`, `moonshot`, `zai`, `qwen`, `perplexity` and a local `ollama` - each reading its provider's conventional environment variable, so switching is `--backend anthropic`. Anything else that speaks the same API works as a `custom` backend with a base URL and a key.
- **The engine is zot's own.** Thread assembly, compaction, four-heuristic loop detection and settle mode are now local Go rather than calls into a hosted service. That is what makes a run inspectable and reproducible offline, and zot no longer depends on any external agent SDK.
- **`agent` is a usable library.** The same engine is importable - `agent.ExecuteWithTools` plus `agent.DefaultTools()` - so an embedder gets thread management, compaction and cycle detection without reimplementing them.
- **Session logs.** Every run is recorded to `~/.local/state/zot/sessions/` as it happens - one JSON object per line, holding the brief, the model, every message and tool call, and how the run ended. An autonomous run is unattended by definition, and this is what turns "it failed overnight" into something answerable. The log is flushed line by line, so it is readable while the run is still going and a killed run still leaves everything up to the kill.
- **`zot --resume`.** The conversation is the entire state of an agent, so writing it down and reading it back is enough to continue a run: `zot --resume last "now add the tests you skipped"`, or `--resume last` on its own to carry on with the original brief. Takes a session id, a path, or `last`. A resumed run writes its own log and records which session it continued.
- **`zot sessions`** lists previous runs, newest first, with the task and how each ended. `--no-session` records nothing; `--session-dir` / `$ZOT_SESSION_DIR` puts the logs somewhere else.
- `zot config` opens the config file in your `$EDITOR`, creating it from a commented template (embedded in the binary) on first run. This is the setup path - choose a backend and model and set your provider key by editing the file. `zot config path` prints the file location.

### Fixed

- **The module path is now `github.com/openzot/openzot`**, matching the repository. It said `github.com/chatbotkit/zot`, which meant `go install github.com/openzot/openzot/cmd/zot@latest` could not work and the version ldflags stamped a symbol that did not exist under the published path.
- The Go toolchain is pinned to 1.26.5. `govulncheck` runs in CI and 1.26.0 carried 13 reachable standard-library advisories - `crypto/x509`, `crypto/tls`, `net/http`, `net/url`, `os` - so the check failed and no release could be cut.
- The container image did not build. The Dockerfile pinned Go 1.25.12 while `go.mod` requires 1.26, and the `golang` images set `GOTOOLCHAIN=local` so the toolchain cannot be fetched - `go mod download` failed before any code was compiled. The release pipeline publishes an image, so this broke releases rather than just local builds.
- A `$VAR` reference in `api_key` was never expanded, so the literal text `$MY_KEY` was sent to the provider and came back as a 401 that reads like a bad key. `api_secret` and `authorization` - the older spellings - did expand, which is why it went unnoticed: the documented spelling was the broken one. All three now resolve, and an unset variable resolves to nothing so the run fails with "no API key configured" instead.
- Token counting was wrong in two ways, both under-counting - the direction that gets a request rejected mid-run. The per-message wire envelope was charged at 4 tokens rather than the 10 OpenAI's own cookbook uses, under-counting a thread of two hundred short messages by more than two thousand tokens; and a tool call's payload was not counted at all, so a request message - which carries no text, only a name and arguments - was priced as an empty message even when writing a whole file.
- The conversation is repaired before it goes on the wire: tool calls and their results are clustered, orphaned halves of a pair are dropped, and empty and duplicate messages removed. Providers reject the whole request rather than the invalid part, so any of these ended an otherwise healthy run with an opaque 400.
- The example config advertised `gpt-5.4-mini` on the `openai` backend after the defaults moved to `glm-5.2` on `zai`, so copying it produced different behaviour from having no config file at all. It now matches, and a test keeps them in step.

### Changed

- **Breaking (config):** a backend credential is written as `api_key` and nothing else. The `api_secret` and `authorization` spellings, the per-model `authorization`, and the convention of inlining a key into the model name (`--model 'gpt-4/authorization=sk-...'`) are all gone - they existed to let configs written for the hosted backends keep working, and those backends are gone. Per-model credentials remain, spelled `api_key`. Three spellings for one field is also what let a real bug hide: `$VAR` expansion worked in two of them and not in the documented one.
- **Breaking (security):** a released binary no longer reads a `.env` from the working directory. zot runs unattended with a provider key and a shell tool, so taking credentials from whatever directory it was pointed at is a liability - running it against a repository you cloned to review was enough to load a stray committed `.env` into the process about to run commands. `make dev` (or `go build -tags dev`) still does, for local development. The switch is a build tag that defaults to off, so a build that forgets it loses a convenience rather than a boundary; `zot --version` prints which kind you have.
- **Breaking (API):** `agent.Message` carries a typed `Activity` instead of a `Meta map[string]any`. A tool call is the only thing zot ever put there, and a map made every read a type assertion that could fail silently and every key a runtime spelling test. Logs written by earlier builds still load - the older nested shape is understood on the way in.
- **Breaking (config):** `features` is gone from the example config. It configured conversation features on a hosted engine that no longer sits in the path; zot talks straight to an OpenAI-compatible provider and has never read it.
- The default model is `glm-5.2` paired with a `zai` default backend - a default pair that cannot talk to each other is worse than no default.
- The default `max_iterations` is now 1,000,000, up from 1,000, so a long autonomous run is not cut short mid-task. The iteration count is no longer the practical bound on a run - the tool-call budget (1,000) and the cycle, empty and continuation guards are what stop one that has gone wrong. Set `--max-iterations` explicitly if you want a hard ceiling on run length.
- The provider package is organised around a `Transport` interface: chat-completions and the Responses API are peers rather than one bolted onto the other, and a future native provider (Anthropic Messages, Bedrock Converse) is one registration with nothing else to change.
- The GitHub organisation profile still described a hosted architecture - "the agentic loop runs on a capable cloud harness", a default ChatBotKit backend, and a link to get a token. All of it predates native backends.
- The example config documents the `ui` section (`diff`, `plain`), which had no example despite both being real settings and flags. `.env.example` no longer advertises removed backends, and says which build actually reads it.
- CI now vets and builds the developer variant too. It is gated behind a build tag, so nothing else in the pipeline ever compiled it - a break there would have surfaced only when someone ran `make dev`.
- `make` prints the available targets instead of assuming `build`. zot has two build variants that differ in what the binary may read from disk, and a bare `make` silently picking one is how you end up debugging a `.env` that was never going to be read. `make vet` now covers both variants, `make cross` defaults to the host, and `make race` / `make cover` were added.

## [0.4.0] - 2026-07-25

### Features

- ACP mode: `zot acp` serves the same agent over the [Agent Client Protocol](https://agentclientprotocol.com/) on stdin/stdout, so an editor or agent harness can drive zot conversationally. Each session works in the directory the client supplies and keeps its own history, `AGENT.md` and skills are resolved per session, and the agent's activity streams back as ACP session updates (message chunks, tool calls, and the `plan`/`progress` tools mapped onto ACP's plan).
- Buzz: `zot acp` is a drop-in agent for [Buzz](https://github.com/block/buzz)'s `buzz-acp` harness - `BUZZ_ACP_AGENT_COMMAND=zot BUZZ_ACP_AGENT_ARGS=acp`.

## [0.3.0] - 2026-06-16

### Features

- Backends: a run now targets a named **backend**. zot ships with two - `cbk` (ChatBotKit, the default) and `relay` (CBK Relay, where you bring your own OpenAI/OpenRouter key) - both speaking the same API. Choose one per run with `--backend` (or `default_backend` in config); otherwise the default is used. The active backend is shown in the header.
- Custom models per backend: under `backends.<name>.models`, a named entry can alias a real model id and override `max_iterations` / `features`. When `--model` matches a key, that entry's settings take priority.

### Changed

- **Breaking (config):** the `chatbotkit:` section is replaced by `backends:`. The credential moves from `chatbotkit.api_secret` to `backends.cbk.api_secret`; `CHATBOTKIT_API_SECRET` still configures the default `cbk` backend with no config file. The `relay` backend's credential is `RELAY_API_KEY`.

## [0.2.0] - 2026-06-16

### Features

- Project context: `AGENT.md` (from the config directory and the working directory) is appended to the agent's backstory, and skills are loaded from `.skills/` or `skills/` in either location and passed to the agent as a `skills` feature.
- Conversation features: enable `web` and `chunking` via repeated `--feature` flags or a `features:` list in the config file (with per-feature options).
- Diff view: `--diff` (or `ui.diff` / `ZOT_UI_DIFF`) renders a framed, syntax-highlighted before/after panel under each edit/write, powered by [chroma](https://github.com/alecthomas/chroma).
- Plain mode: when stdout is not a TTY (piped, CI, driven by another program) zot streams unstyled output instead of the full-screen UI; force it with `--plain` (or `ui.plain` / `ZOT_UI_PLAIN`).

### Changed

- Default model is now `kimi-k2.7-code`, and the default iteration cap is `1000`.
- zot now builds against the published `github.com/chatbotkit/go-sdk` release; local development against an SDK checkout uses a gitignored `go.work`.

## [0.1.0] - 2026-06-15

### Features

- Initial release of `zot`, an autonomous coding agent. Brief it once and it works the problem on its own - reading files, editing them, and running shell commands - while a read-only view streams every step. No prompting, no babysitting.
- Autonomy is driven by the ChatBotKit Go SDK's `agent.ExecuteWithTools` loop (plan → act → observe → progress → exit) with `agent.DefaultTools()` (`read`, `write`, `edit`, `exec`) as the coding toolbox.
- Read-only [Bubble Tea](https://github.com/charmbracelet/bubbletea) viewer with a scrollable activity log, per-tool styling, live narration, and a header showing model, working directory, iteration, tool, and edit counters plus elapsed time. The UI has no text input by design.
- Layered configuration: built-in defaults < `~/.config/zot/config.yaml` < `ZOT_*` environment variables, with the API secret read from the platform-standard `CHATBOTKIT_API_SECRET`. CLI flags (`--model`, `--dir`, `--max-iterations`, `--task-file`, `--config`) override the resolved config.
